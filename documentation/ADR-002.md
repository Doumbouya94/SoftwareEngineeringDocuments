# Architecture Decision Records ADR-002 — Choix du pattern architectural MVVM

**Statut :** Accepted

**Date :** 2026-01-23

**Décideurs :** Pierre-Sylvestre Cypré, Aboubacar Doumbouya Sidiki

**Contexte projet :** EventGo — Application mobile de découverte d'événements locaux

---

## 1. Contexte

- **Problème / besoin :** Suite au choix de .NET MAUI comme framework (ADR-001), nous devons choisir un pattern architectural pour structurer le code de l'application EventGo. L'architecture doit permettre une séparation claire des responsabilités, faciliter les tests unitaires, et supporter le data binding natif de MAUI.
- **Contraintes :**
    - **Framework :** Application en .NET MAUI avec C# et XAML
    - **Testabilité :** Besoin de tests unitaires pour respecter NFR-4 (couverture minimale)
    - **Maintenabilité :** Code facile à comprendre et à faire évoluer pour une petite équipe
    - **Délais :** Pattern qui ne ralentit pas le développement (phases jusqu'en avril 2026)
    - **Équipe :** 2 développeurs avec expérience C# mais familiarité variable avec les patterns architecturaux
- **Forces en présence :**
    - Besoin de séparer la logique métier de l'interface utilisateur
    - Mise à jour réactive de l'UI en fonction des changements de données
    - Facilité de test de la logique métier sans dépendance à l'UI
    - Support natif du pattern par MAUI et outillage Visual Studio

---

## 2. Décision

> Nous choisissons le pattern **MVVM (Model-View-ViewModel)** comme architecture pour l'application EventGo.
> 
- Nous choisissons : MVVM (Model-View-ViewModel) avec CommunityToolkit.Mvvm
- Pour : Structurer le code avec une séparation claire entre UI (View), logique de présentation (ViewModel), et données (Model), tout en tirant parti du data binding natif de MAUI

---

## 3. Alternatives considérées

### Option A — MVVM (Model-View-ViewModel)

- **Avantages :**
    - Séparation claire des responsabilités (Model, View, ViewModel)
    - Support natif dans .NET MAUI avec data binding XAML
    - ViewModels testables unitairement sans dépendance à l'UI
    - Pattern recommandé par Microsoft pour MAUI
    - Excellente documentation et exemples disponibles
    - Support via CommunityToolkit.Mvvm (ObservableObject, RelayCommand)
    - Mise à jour automatique de l'UI via INotifyPropertyChanged
    - Réutilisation possible des ViewModels entre différentes Views
- **Inconvénients :**
    - Courbe d'apprentissage initiale pour les concepts (binding, commands, observables)
    - Code boilerplate pour les propriétés observables (réduit avec CommunityToolkit)
    - Peut être sur-architecturé pour des écrans très simples

### Option B — MVC (Model-View-Controller)

- **Avantages :**
    - Pattern classique et bien connu
    - Simple à comprendre conceptuellement
    - Séparation entre données (Model), UI (View), et logique (Controller)
- **Inconvénients :**
    - Moins adapté au data binding bidirectionnel de MAUI
    - Controller devient rapidement monolithique
    - Difficile à tester sans mock de l'UI
    - Pas le pattern standard recommandé pour MAUI
    - Nécessite plus de code manuel pour la synchronisation UI/données

### Option C — Code-behind pur (sans pattern formel)

- **Avantages :**
    - Simplicité initiale maximale
    - Pas de concepts architecturaux à apprendre
    - Développement rapide pour des écrans très simples
- **Inconvénients :**
    - Mélange logique métier et UI dans le même fichier
    - Impossible à tester unitairement (dépendance à l'UI)
    - Difficile à maintenir quand le code grandit
    - Duplication de logique entre les pages
    - Ne respecte pas les bonnes pratiques .NET MAUI
    - Bloque l'atteinte de l'objectif NFR-4 (tests unitaires)

---

## 4. Justification (Pourquoi cette décision ?)

- **Standard .NET MAUI :** MVVM est le pattern officiellement recommandé par Microsoft pour MAUI, garantissant un alignement avec les bonnes pratiques et la documentation
- **Testabilité :** Les ViewModels peuvent être testés unitairement sans instancier l'UI, permettant d'atteindre l'objectif NFR-4 de couverture de tests
- **Data Binding natif :** MAUI supporte nativement le binding XAML ↔ ViewModel, réduisant le code manuel et les erreurs de synchronisation UI/données
- **Séparation des responsabilités :** Découpage clair Model (entités + data access) / View (XAML + UI) / ViewModel (logique de présentation), facilitant la maintenance et l'évolution
- **CommunityToolkit.Mvvm :** Bibliothèque Microsoft officielle qui réduit considérablement le boilerplate avec des attributs source generators ([ObservableProperty], [RelayCommand])
- **Réutilisabilité :** Un même ViewModel peut être utilisé par plusieurs Views (ex: EventDetailViewModel partagé entre version mobile et tablette)
- **Expérience de l'équipe :** L'équipe a déjà une base en C# et .NET, MVVM s'intègre naturellement dans cet écosystème
- **Outillage :** Visual Studio offre un excellent support pour MVVM (IntelliSense, refactoring, debugging des bindings)

---

## 5. Conséquences

### Positives

- Code structuré et maintenable avec séparation claire des responsabilités
- Tests unitaires possibles sur toute la logique métier (ViewModels, Services, Repositories)
- Mise à jour automatique de l'UI via data binding et INotifyPropertyChanged
- Réduction du code boilerplate grâce à CommunityToolkit.Mvvm
- Facilite le travail en équipe (un dev sur Views, l'autre sur ViewModels/Services)
- Permet l'évolution future (ex: ajouter une version desktop qui réutilise les ViewModels)
- Documentation et exemples abondants dans la communauté MAUI

### Négatives / Risques

- Courbe d'apprentissage initiale pour les concepts MVVM (binding, commands, observables)
- Peut sembler sur-architecturé pour des écrans très simples (ex: About page)
- Nécessite discipline pour ne pas contourner le pattern (éviter code-behind)
- Potentiel de memory leaks si les bindings ne sont pas correctement gérés

### Impact sur l'architecture / le code

**Structure des dossiers :**

```
EventGo/
├── Models/            # Entités métier (Event, User, Favorite, Category)
├── ViewModels/        # Logique de présentation (EventListViewModel, EventDetailViewModel, etc.)
├── Views/             # XAML + code-behind minimal (EventListPage.xaml, EventDetailPage.xaml, etc.)
├── Services/          # Services métier (EventService, AuthService, LocationService, etc.)
└── Repositories/      # Accès aux données SQLite
```

**Modules touchés :**

- **Auth :** LoginViewModel, RegisterViewModel → LoginPage, RegisterPage
- **Events :** EventListViewModel, EventDetailViewModel, EventFilterViewModel → EventListPage, EventDetailPage
- **Favorites :** FavoritesViewModel → FavoritesPage
- **Profile :** ProfileViewModel, OrganizerDashboardViewModel → ProfilePage, OrganizerDashboardPage
- **Admin :** AdminDashboardViewModel → AdminDashboardPage

**Dépendances :**

- Ajout de `CommunityToolkit.Mvvm` NuGet package
- Configuration de l'injection de dépendances (DI) pour ViewModels et Services

**Conventions :**

- ViewModels héritent de `ObservableObject` (ou utilisent attributs source generators)
- Propriétés observables avec `[ObservableProperty]`
- Commandes avec `[RelayCommand]`
- Services injectés via constructeur dans les ViewModels
- Views ont une référence à leur ViewModel via `BindingContext`

## 7. Validation

- **Comment vérifier que c'est bon ?**
    - Chaque ViewModel peut être instancié et testé unitairement sans dépendance à l'UI
    - Les propriétés observables déclenchent bien `PropertyChanged` et mettent à jour l'UI
    - Les commandes (RelayCommand) sont correctement liées aux boutons et actions utilisateur
    - Les Services sont correctement injectés via DI dans les ViewModels
    - Aucun code métier n'est présent dans les fichiers code-behind (.xaml.cs)
    - Le data binding fonctionne dans les deux sens (UI → ViewModel et ViewModel → UI)
    - Tests unitaires couvrent au minimum : LoginViewModel, EventListViewModel, EventDetailViewModel, FavoritesViewModel
    - Pas de memory leaks détectés avec le profiler Visual Studio
    - Navigation entre pages fonctionne via commandes dans les ViewModels
